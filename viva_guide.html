Big picture

E1Explain the overall architecture of your project.

There are three programs. scheduler is the main process. Inside it, the dispatcher (main thread) owns the clock and decides who runs, an arrival thread moves jobs into the ready queue at their arrival time, and there is one thread per job.

The scheduler forks a logger process and sends it events through a pipe; the logger writes them to schedule.log. At the end, the scheduler forks and execs a report process and passes it the final metrics through shared memory, guarded by a semaphore.

main: load_jobs → logger_start → run_algorithm (×1 or ×4) → report_run → logger_stop
E2How does your program make sure only one job uses the CPU at a time?

Every job thread blocks on its own semaphore run_sem[i] (initial value 0). Only the dispatcher posts it, and it posts exactly one job, then immediately blocks on sem_wait(done_sem). It does not decide again until that job posts done_sem. So at any moment at most one job thread is awake.

E3Walk through one time unit of the dispatcher.
  • Set clock = t, sem_post(tick_sem), sem_wait(arrived_sem). The arrival thread queues every job with arrival ≤ t.
  • Lock the mutex, call pick_next() (the algorithm decides), unlock.
  • If nothing is ready, the CPU is IDLE for one unit.
  • If the chosen job differs from the last one, count a context switch.
  • sem_post(run_sem[job]), sem_wait(done_sem). The job runs one unit.
  • t++, update the Gantt chart; if remaining is 0, record completion.
E4Trace jobs1.txt with Round Robin, quantum 2.

P1(0,5), P2(1,3), P3(2,8).

  • 0–2 P1. At t=2, P3 arrives first, then P1 is preempted. Queue: P2, P3, P1.
  • 2–4 P2 → queue P3, P1, P2. 4–6 P3 → P1, P2, P3. 6–8 P1 → P2, P3, P1.
  • 8–9 P2 finishes (only 1 left). 9–11 P3. 11–12 P1 finishes. 12–16 P3 alone.

Completion 12, 9, 16. Averages TAT 11.33, WT 6.00, RT 1.00. Context switches: 7.

Synchronisation

E5What does your mutex protect?

Sim.lock protects everything the threads share: the ready queue, the clock, the released counter, and each job's changing fields (remaining, first_start, completion). A second mutex, log_lock, protects writes to the pipe so log lines from two threads never mix.

E6List your semaphores and their initial values.
SemaphoreInitMeaning
run_sem[i]0dispatcher → job i: you may run
done_sem0job → dispatcher: my unit is finished
tick_sem0dispatcher → arrival thread: clock is now t
arrived_sem0arrival thread → dispatcher: arrivals for t queued
/mini_sched_ready_<pid>0named, between processes: report may read shared memory

All start at 0 because each one means "an event has happened", and at the start nothing has happened yet.

E7What is the difference between a mutex and a semaphore? Why did you use both?

A mutex is a lock: the thread that locks it must unlock it, and it protects a critical section. A semaphore is a counter that any thread can post and any thread can wait on, so it is used for signalling between threads (one thread tells another "go").

We use the mutex to protect shared data, and semaphores for the handoff between dispatcher, arrival thread and job threads.

E8What is busy waiting and how did you avoid it?

Busy waiting is a loop that keeps checking a variable while burning CPU (e.g. while(!ready);). Every wait in our code is sem_wait, pthread_mutex_lock, pthread_join or waitpid, which put the thread to sleep. nanosleep is used only to simulate one unit of work or idle time. A full run uses about 0% CPU.

E9What is a data race? How do you know you have none?

Two threads access the same variable at the same time, at least one writes, and there is no synchronisation. Every shared variable is accessed under the mutex or protected by the semaphore protocol. We built the program with GCC's ThreadSanitizer (-fsanitize=thread) and ran all inputs in all mode: zero warnings.

E10What is a deadlock? Can your program deadlock?

Deadlock is when threads wait for each other forever. The only place two locks are held together is Sim.lock then log_lock (when log_event is called while holding the main lock). That order is always the same and never reversed, so a cycle cannot form. Each semaphore post has exactly one matching wait.

Processes and metrics

E11What is the difference between fork() and exec()?

fork() creates a copy of the current process; both continue from the same point (returns 0 in the child, the child's pid in the parent). exec() replaces the current process's program with a new program; the pid stays the same and open file descriptors stay open unless marked close-on-exec. We fork, then exec ./logger and ./report in the child.

E12What is a zombie process and how do you avoid one?

A child that has exited but whose parent has not collected its exit status. We call waitpid() on both the logger and the report process, so neither is left as a zombie.

E13Give the formulas for turnaround, waiting and response time.
  • Turnaround = completion − arrival
  • Waiting = turnaround − burst
  • Response = first time on CPU − arrival

For non-preemptive algorithms (FCFS, SJF) waiting equals response, because a job runs to completion once it starts.

E14What counts as a context switch in your program?

The CPU going from one job directly to a different job. The first dispatch is not counted, and switches to or from IDLE are not counted. If RR's quantum ends and no one else is waiting, the same job continues: no switch.

E15Which algorithm is best? Look at your results.

It depends on the goal. SRTF gives the lowest average waiting and turnaround (jobs4: 7.30 vs FCFS 25.90) but can starve long jobs (jobs5: P1 waits 18). RR gives good response time (fair, interactive) but the most context switches (jobs4: 25). FCFS is simple but suffers the convoy effect when a long job arrives first.

Live execution · engine.c

U1Why does the dispatcher give the CPU one time unit at a time instead of a whole slice?

So it can make a decision at every time boundary. SRTF must preempt the moment a shorter job arrives, and RR must queue a new arrival before the preempted job at the exact tick. With unit-by-unit dispatch both rules happen naturally; the job thread still does all the "running" and printing, exactly as in Figure 2.

U2Why do you need the tick/arrived handshake? What would go wrong without it?

Without it, the arrival thread and the dispatcher would race: at time t the dispatcher might call pick_next() before the arrival thread has queued a job that arrives at t. The result would change from run to run. With RR, the preempted job could end up before the new arrival, breaking the brief's rule. The handshake guarantees: all arrivals for t are queued before any decision at t.

U3What is a job thread doing when it is not running?

It is blocked inside sem_wait(&run_sem[i]). The OS puts it to sleep, so it uses no CPU. It wakes only when the dispatcher posts its semaphore.

U4Show the job thread loop and explain each line.
do {
  sem_wait(&run_sem[i]);      // wait for the CPU
  lock; print "[t] Pi running"; unlock
  sleep_unit();                // simulate 1 unit of work
  lock; rem = --remaining; unlock
  sem_post(&done_sem);         // give the CPU back
} while (rem > 0);             // done → thread returns

It prints the remaining time before the unit, matching the sample output.

U5How do threads end and why do you join them?

A job thread returns after its last unit (remaining reaches 0). The arrival thread returns after it has released all jobs. The dispatcher calls pthread_join on all of them, which waits for them and frees their resources. Only after joining do we compute metrics, so no locking is needed there.

U6How is idle time handled?

If pick_next() returns -1, nothing is ready. The dispatcher prints CPU IDLE, adds an IDLE segment to the Gantt chart, sleeps one unit, increments t and loops. It still posts tick_sem every unit, so jobs arrive on time. The loop cannot spin forever because unfinished jobs must still be on the way.

U7In all mode, do you reuse threads between algorithms?

No. Each call to run_algorithm() allocates a fresh Sim, copies the original jobs, creates new threads, semaphores and mutex, and destroys them all at the end. The four runs are completely independent.

U8What if the dispatcher posted two run semaphores at once?

Two jobs would run at the same time, which is impossible on one CPU, and their output and timing would mix. That is why the dispatcher always posts one and waits for done_sem before doing anything else.

Algorithms · algorithms.c

U9How does pick_next() work for each algorithm?
  • FCFS / SJF (non-preemptive): if a job is running, return it. Otherwise pick lowest arrival (FCFS) or lowest burst (SJF).
  • SRTF: find the lowest remaining in the queue; preempt only if it is strictly less than the running job's remaining.
  • RR: keep the running job while quantum_used < q. When the quantum is used and someone is waiting, push it to the back and take the front.
U10How are ties broken?

In better(): first the algorithm's key (arrival / burst / remaining), then earlier arrival, then smaller id. Ids are compared with job_id_cmp(), a "natural" comparison, so P2 < P10 (plain strcmp would say P10 < P2).

U11In SRTF, what happens if a new job's remaining time equals the running job's?

The running job continues. We preempt only with a strict <, as the brief says. This also avoids a pointless context switch.

U12In RR, what if the quantum expires and the ready queue is empty?

The same job continues with a fresh quantum (quantum_used = 0). It is not preempted and no context switch is counted. You can see this in jobs1 from t=12 to 16, where P3 runs alone.

U13Where can starvation happen and why?

In SJF and SRTF. If short jobs keep arriving, a long job is never the shortest and keeps waiting. jobs5.txt shows it: P1 (burst 10) gets no CPU until t=18. FCFS and RR cannot starve a job: FCFS serves by arrival order, and RR gives every job a turn each round. Aging (raising priority over time) is the usual fix.

Main program · scheduler.c

U14What checks does main() do on the command line?

There must be 2 or 3 arguments; the algorithm must be fcfs, sjf, srtf, rr or all; the quantum must be a positive whole number. If no quantum is given for rr/all, it uses 2 and prints a note. Any error prints a message and exits with code 1.

U15Why does main() ignore SIGPIPE?

If the logger died, writing to the pipe would send SIGPIPE, whose default action kills the scheduler. With SIG_IGN, write() just returns an error (EPIPE) and we drop the log line; the scheduling continues.

Job table · jobtable.c

T1How do you parse each line of the input file?

Read with fgets; cut everything after # (comments); split on spaces/tabs with strtok_r. Blank lines are skipped. There must be exactly 3 tokens: id, arrival, burst. Numbers are converted with strtol.

T2What bad input do you reject?
  • Missing or unreadable file (message from strerror(errno))
  • Empty file or only comments: "contains no jobs"
  • Wrong number of fields, values that are not whole numbers
  • Negative arrival or burst, burst of 0
  • Duplicate ids, id longer than 15 characters, the reserved id IDLE
  • More than 64 jobs, or times above 10000

Each message includes the line number, and the program exits with code 1.

T3How do you detect that "3.5" or "one" is not a valid number?

strtol sets an end pointer to the first character it could not use. We require that the end pointer moved (something was read) and that it points to '\0' (nothing left over). For "3.5" the end stops at ".", for "one" it does not move, so both are rejected. We also check errno == ERANGE for overflow.

T4Why reject a burst time of 0 and the id IDLE?

A job with burst 0 never needs the CPU: its thread would have nothing to run and its metrics would be meaningless. IDLE is the label we use in the Gantt chart for an idle CPU, so a job with that name would be confused with idle time.

T5The input is not sorted. How do you handle that?

The job table keeps file order. In run_algorithm() we build an order[] array of job indices sorted by (arrival, id) with qsort. The arrival thread walks that array, so jobs are released in the right order whatever the file looks like. jobs3 and jobs4 are deliberately unsorted.

T6Which struct stores a job, and what is each field for?

Job: id, arrival, burst (from the file); remaining (decreases while running); first_start (−1 until first dispatch, for response time); completion (−1 until finished).

Output and metrics · output.c

T7How is the Gantt chart built?

After every unit the dispatcher calls gantt_add(id, t). If the last segment has the same id and ends at t, it is extended by one; otherwise a new segment {id, start, end} is added. So "P1 P1 P2 P2" becomes two segments: P1 0–2, P2 2–4.

T8How does print_gantt() line up the times under the boxes?

Each box gets a width big enough for both its label and its start time (minimum 4). The time row prints each segment's start, left-aligned in the same width + 1 for the |, then the final end time. Long charts are split into rows of about 72 characters.

T9Where are the metrics calculated and printed?

Calculated in engine.c after all threads are joined (turnaround, waiting, response and their averages). Printed by print_job_table() and print_comparison() in output.c. The report program calls them on data read from shared memory. output.c is linked into both the scheduler and the report.

T10When is waiting time equal to response time?

When a job is never preempted: once it starts it runs to the end, so all its waiting happens before its first run. That is always true for FCFS and SJF. In RR or SRTF a job can wait again after it started, so waiting can be larger than response.

T12Why do the algorithms differ so much on jobs4?

A 20-unit job (P1) arrives first, followed by many short jobs. FCFS makes them all wait behind P1 (the convoy effect): avg waiting 25.90. SJF is also stuck behind P1 because it is non-preemptive (20.30). SRTF preempts P1 for each short job (7.30). RR shares the CPU evenly (14.50) but needs 25 context switches.

T13In jobs2, why does RR have the worst waiting time but the best response time?

Every job gets the CPU within the first few slices (good response: 4.00), but all jobs are interleaved, so every job finishes late (worst waiting: 16.80). SJF finishes short jobs first, which minimises average waiting (8.60).

Logger process · Part 5

A1Explain logger_start() step by step.
pipe(fds)                  // fds[0] read end, fds[1] write end
fork()
child:  close(fds[1])      // child only reads
        dup2(fds[0], 0)    // pipe becomes stdin
        close(fds[0])
        execl("./logger", "logger", "schedule.log")
parent: close(fds[0])      // parent only writes
        log_fd = fds[1]
A2What does dup2() do, and why use it?

dup2(old, new) makes file descriptor new refer to the same file as old (closing new first). dup2(fds[0], STDIN_FILENO) makes the pipe's read end become fd 0. The logger then just reads its standard input with fgets(stdin); it does not know or care that it is a pipe.

A3Why must unused pipe ends be closed?

A reader only sees EOF when every write end is closed. If the logger kept its own copy of the write end open, it would never get EOF and would wait forever. Closing the unused read end in the parent is good hygiene and frees the descriptor.

A4How does the logger know when to stop?

logger_stop() closes the write end. The logger's fgets returns NULL (EOF), the loop ends, it writes a footer, closes the file and exits. The scheduler then calls waitpid on it, so no zombie is left.

A5Why set FD_CLOEXEC on the pipe?

The report process is started later with fork + exec. Without close-on-exec it would inherit the pipe's write end and keep it open, so the logger would not see EOF until the report also exited. With FD_CLOEXEC the descriptor is closed automatically at exec. (dup2 clears the flag on the logger's new fd 0, so its stdin stays open.)

A6Which events are logged, and why is log_lock needed?

Job arrived, started, resumed, preempted, finished, plus CPU idle and run headers. Two threads call log_event(): the arrival thread and the dispatcher. log_lock makes each line one uninterrupted write so lines never mix, and it protects log_fd while logger_stop() closes it.

A7Why call fflush(stdout) before fork()?

printf output is buffered in the process's memory. fork() copies that memory, so unflushed text would be printed twice, once by each process. Flushing first empties the buffer.

Shared-memory report · Part 6

A8Which shared memory did you use? Explain the calls.

POSIX shared memory.

  • shm_open(name, O_CREAT|O_EXCL|O_RDWR, 0600): create the object
  • ftruncate(fd, sizeof(SharedReport)): give it a size (a new object has size 0)
  • mmap(..., MAP_SHARED, fd, 0): map it into memory, so writes are visible to the other process
  • At the end: munmap, close, shm_unlink

The report does the same with O_RDONLY and PROT_READ.

A9Explain the order of events in report_run().
  • Create the shared memory and the named semaphore (value 0).
  • fork + exec ./report shm_name sem_name. The report attaches and blocks on sem_wait.
  • The scheduler memcpys all results into shared memory, then sem_post.
  • The report wakes up, prints the final report and exits; the scheduler waitpids and cleans up.
A10Why start the report before writing the data?

To show that the semaphore really does the synchronisation. If we wrote first and then started the report, it would work even without the semaphore. Started first, the report would read empty or half-written data unless it waits for the post.

A11Why a named semaphore instead of sem_init?

After exec the report is a different program with a fresh address space, so it cannot use a semaphore variable from the scheduler's memory. A named semaphore (sem_open with a name) can be opened by any process that knows the name. (An unnamed semaphore placed inside the shared memory with pshared = 1 would also work.)

A12Why does the name contain the pid? Why O_EXCL?

The pid makes the name unique, so two students running the program at the same time on a lab machine do not share or destroy each other's segment. O_EXCL makes creation fail if the name already exists, so we never silently reuse old data.

A13What happens if you forget shm_unlink / sem_unlink?

POSIX shared memory and named semaphores live in the kernel (visible under /dev/shm) until unlinked or until reboot, even after the program exits. That leaks memory. make test checks /dev/shm to prove nothing is left.

A14How does the scheduler find ./logger and ./report?

It reads /proc/self/exe (the path of the running program) and takes its directory. So it works even if you run it from another folder, e.g. ../scheduler jobs.txt fcfs.
